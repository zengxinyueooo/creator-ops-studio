# 口述稿·口语版

> 和《面试讲述-主线叙事版》第六节是替代关系:那一版是"写得对",这一版是"说得出口"。
> 原则:一句话一个意思。术语第一次出现必须用白话解释。细节不讲,等追问。
> 【】里是要你自己填的真实数字,填完再练。

## 练习方法

1. 不要背字,背"路标":下面每个小标题是一个路标,路标之间自己组织语言。
2. 每段录音讲一遍,听一遍,把拗口的句子改短。
3. 计时:全程目标 4 分钟以内,两个故事共 90 秒。

---

## 路标一:我做内容时在烦什么(约 30 秒)

我实习做过小红书运营,自己也养了一个漫画号。

做一篇内容,流程大概是这样:先搜别人发过这部漫画没有,把觉得好的帖子存下来,图片一张张存到本地文件夹,再自己记着"这张图是第几话的"。然后想选题、写文案、发出去。

听着不难。但做内容时常有这些问题:参考帖存在收藏夹里,图片存在文件夹里,选题记在表格里——三边对不上。做到一半电脑出问题,我不记得采集到哪张图了,只能重来。发完了,也说不清这篇内容当时参考了谁。

我的痛点不是"AI 会不会写文案",是**过程没有系统管**。

## 路标二:所以我做了什么(约 30 秒)

我做了一个工作台,把这条流程整个装进去。

从漫画库、调研参考、采集素材,到选题、Brief、草稿,现在还可以把选好的图片和文案暂存进小红书创作者中心。我打开草稿检查、修改,最后自己发布。系统里能看到前面各步做到哪了、卡在哪、失败了从哪继续。

它不是自动发帖机器人。Brief 审核和选图由我决定;AI 帮我完成调研、整理和草稿准备;暂存到创作者中心也要我主动点击,最后的修改和公开发布仍由我完成。

## 路标三:技术上怎么搭的(约 45 秒)

前端 React,数据在 Supabase,认证、数据库、图片存储、用户隔离都是它管。

有意思的是后半段。第一版很简单:页面收输入,拼个 Prompt,调一次模型。对写文案这种一步到位的任务,这样就够了。

但后来发现采集素材是另一回事。它要开浏览器、读正文、一张张图处理、存库。中途随时可能断。这种任务塞在按钮里根本管不了。

所以我把它改成了后台任务:页面只负责往数据库里塞一条任务,一个 Worker 领出来跑。Worker 按"这是哪种任务"加载对应的操作手册和工具白名单,再启动一个 Agent 会话去执行。**Agent 能用什么工具、能碰哪个用户的数据,都是代码定的,不是 Prompt 定的。**

跑完还不算完——模型说"我做完了"不算数,程序去查数据库,该有的记录都在,才算成功。

## 路标四:两个真实的事故(约 90 秒)

讲两个我踩过的坑,都挺典型的。

**第一个:** 有次一个采集任务半天没动静。我第一反应是模型额度又不够了,之前确实老遇到。但我没直接重试,去查了任务记录——它的领取次数是零。就是说,它压根没被任何 Worker 领走过,跟模型一点关系没有。是 Worker 挂了。我把 Worker 拉起来,这次才真的遇到额度错误——两个完全不同的故障,表现一模一样。

这件事之后,我把"排队中""运行中""业务失败"彻底分开了,页面会给不同的提示和不同的建议,Worker 断线也改成退避重连而不是直接退进程。

**第二个:** 我加了任务表之后,一度觉得系统已经稳了。后来意识到一个漏洞:如果一个 Worker 卡在模型调用上,租约超时,任务被别的 Worker 接走——旧的 Worker 醒过来,还会往里写。也就是说,**把任务存进数据库,不等于执行是安全的**。

解决办法是把并发控制下沉到数据库:同一时间同一个对象只允许一个活动中的任务,用唯一索引卡住;Worker 写结果前必须验明"这任务现在还归我管";素材写入用固定位置,处理过的直接跳过。有一次真实运行,一篇笔记七张图已经存了一张,系统接着补了剩下六张,最后核验一到七每张恰好一条,没有重复。

## 路标五:怎么验证的、现在到什么程度(约 40 秒)

验证我分了三层:工程层,54 个自动化测试,加上构建和类型检查全过;数据层,直接查真实库,完整采集的七篇参考图片位置全齐,四十九条素材没有位置重复;业务层,坦白讲还没做完——我留着失败样本,十九次历史任务里六成十三败,但这些跨了好几个开发版本,我不会拿它说当前成功率。

使用层面我会分开讲:我已经用真实账号和真实数据跑过调研、素材整理,也试过把一份草稿暂存进创作者中心;但我目前发笔记时仍会重新核对素材,还没有把它当作每天固定使用的发布流程。它现在证明的是流程可用,还不能拿日常使用率或节省多少小时当结果。模型花费【查账单后填写】,Supabase 费用【查后台后填写】。

还差的主要是:Worker 还不是系统服务,重启电脑要手动拉起;最新版本六类任务还没做系统化的真实验收。这两件是我接下来要做的。

## 路标六:收尾——我的角色(约 20 秒)

整个过程里 AI 写了大量代码,我不回避这个。但需求是我从自己的运营经历里拆出来的,哪些不做、状态怎么定义、失败怎么分类、什么算成功,这些判断是我的。

我认为这恰恰是 AI Coding 的正确用法:**模型负责快,我负责对。**

## 追问速记卡(数字都在代码里,背熟)

| 追问 | 答案 | 出处 |
|---|---|---|
| 轮询间隔多少 | 默认 2.5 秒,可配,下限 1 秒 | worker.ts `AGENT_WORKER_POLL_MS` |
| 租约多久 | 10 分钟,每次写进度事件时续租 | `renew_agent_run_lease` |
| 租约过期会怎样 | 任务可被重新领取;旧 Worker 写入时必须匹配 worker_id 且状态还是 running,否则写不进去 | `finish_agent_run` / lease guard 迁移 |
| 重试策略 | 最多 3 次,500ms 起指数退避;只重试只读的瞬时错误,写操作不自动重放 | retryPolicy.ts |
| 并发去重怎么做 | 部分唯一索引:(user_id, run_type, target_type, target_id),条件 status in (queued, running);冲突时复用已有任务 | `agent_runs_one_active_target_idx` |
| 怎么原子领取 | `FOR UPDATE SKIP LOCKED` | agent_execution.sql:76 |
| 测试规模 | 17 个文件 54 个用例,全过(2026-09-24 实测) | vitest |
| 单图恢复怎么核验 | 每个预期位置恰好一条素材,多一条少一条都不算完成 | finalize 核验 |

## 新增追问答案骨架(之前文档没有的,先填数字再练)

### "你自己真的在用吗?省了多少时间?"

> 我用真实账号和真实数据验证过调研、素材和草稿暂存,但目前还没有把它变成每天固定用的发布流程。原因是参考图片不等于可以直接发布的成品,我仍会核对重复、授权和画面适配,必要时自己找或替换素材。所以我现在讲的是它减少了资料整理和反复搬运,以及让我能从系统草稿进入创作者中心继续编辑;具体省了多少时间,等固定样本的人工对照做完再报数字。

### "成本怎么样?"

> 分三块:模型、Supabase、机器。模型是大头,【单次采集任务约 X token / X 元】【每月约 X 元】;遇到额度错误后我加了错误分类,额度类错误不再消耗重试。Supabase【免费档够用 / 每月 X 元】。OpenCLI 复用本机已登录浏览器,零额外成本。这个规模下总成本【X 元/月】,比我实习时的时薪低,所以划算。

(练之前打开 Supabase 后台和模型账单,把 X 填成真数。**这个题空手回答的代价最大。**)

### "为什么不用 Dify / Coze / n8n 这类平台搭?"

> 我评估过【如果没评估过,现在花半小时过一遍再答】。这类平台搭"调一次模型"的流程很快,但我的核心问题是任务可靠性:队列、租约、并发去重、逐图恢复、执行权和数据库核验,这些它们要么没有,要么得绕开平台自己写。而且我的数据模型是业务领域的——参考、素材、选题、Brief 各有状态机,平台的多维表格表达不了这种状态流转和约束。所以选了代码直写:前期慢,但可靠性机制全部可控。

### "Pi Agent 是什么?为什么用它?"

> 它是一个开源的 Agent SDK,提供会话管理、工具调用循环和 Skill 加载。我需要的就是这三样,而不用自己从零写工具调用循环和上下文管理。选它而不是 LangChain 这类,是因为【真实理由,如:我在它的代码库里验证过 Skill/工具白名单机制 / 它的会话模型更贴近我的单任务单会话设计】。本质标准是:Agent 框架对我来说是"执行器",权限和状态都在我自己的代码和数据库里,框架可替换。

### "这个项目做了多久?"

> 【X 周/X 个月】,99 个提交。前期主要是数据模型和页面,后面一半时间都在补可靠性——这个比例我覺得很正常,长任务系统就是这样。
