# Creator Ops Studio：AI Coding 项目面试主线叙事版

> 使用方式：这份文档用于现场讲述，强调故事主线、个人判断和 AI Coding 方法；`面试讲述-Creator-Ops-Studio.md` 用作技术细节与追问手册。两份文档不是互相替代，而是“主讲稿 + 答辩资料”。

## 一、先给全景：让面试官在一分钟内看懂

### 1. 一句话介绍

我做了一个面向个人创作者的 AI 内容运营工作台，把原本散落在浏览器、收藏夹、图片文件和临时文档里的漫画调研、素材整理、选题、Brief 和草稿生产，变成了一条可追踪、可恢复、有人审关卡的工作流。

它不是自动发小红书的工具，也不是输入一句话就生成文案的 Demo。它解决的是发布前最耗时、最容易混乱的内容准备过程。

### 2. 用户与场景

第一用户就是我自己。我实习时做过小红书选题、素材、生图、文案和发布的全流程，自己也运营漫画账号。

典型场景是：我发现一部值得做的漫画，需要查看别人发过哪些片段、判断哪些角度有内容价值、保存参考帖和图片、找到对应章节、形成选题与 Brief，再生成草稿。审核选图后，我可以主动把图片和文案暂存到小红书创作者中心，继续修改，再手动发布。

这不是一个虚构需求。它来自我实际做过的运营动作，因此我能够判断什么功能有用、哪些自动化反而会增加风险。目前我用真实数据验证过流程，但日常发帖时仍会人工核对并替换不适合直接使用的参考素材，不能把“跑通”说成“每天都在用”。

### 3. 没有这个系统之前怎么做

原来的流程主要依赖：

- 浏览器临时搜索和收藏；
- 本地文件夹保存图片；
- 靠记忆判断素材属于哪部漫画、哪个章节；
- 临时参考其他笔记的标题和结构；
- 用表格或零散文档记录选题；
- 发布后很难追溯一篇内容基于哪些参考和素材。

它带来四类问题：

1. **信息散落**：参考、正文、图片、选题和文案彼此断开。
2. **过程不可追踪**：不知道一篇笔记采集到哪一步，刷新或失败后容易重做。
3. **结果不可追溯**：无法准确说明一个 Brief 使用了哪些证据和素材。
4. **AI 只能完成局部生成**：模型可以写一段文案，但无法稳定完成有前置条件、多个副作用和人工审核的业务步骤。

### 4. 最终形态是什么

最终是一个可以登录、切换账号和实际操作的 Web 工作台，包含：

- 漫画库与官方知识档案；
- 小红书参考调研与人工筛选；
- 笔记正文和图片素材采集；
- 素材来源、位置和使用记录；
- 选题看板；
- 结构化 Brief 生成与人工审核；
- 多版本草稿生成；
- 人工触发的创作者中心草稿暂存，供最终修改与手动发布；
- 任务进度、失败原因和恢复操作；
- 内容日历和效果复盘基础页面。

底层采用“通用内容运营内核 + 漫画垂直首发”。第一条完整链路先服务漫画账号，但账号、选题、参考、素材、草稿和指标等模型可以复用到我的“求职 + 学习 + 技术”账号。

### 5. 一张图讲清系统

```text
人工发起与审核
      ↓
React 内容工作台
      ↓ 创建任务 / 展示进度
Supabase：业务数据 + Agent 任务 + 私有图片
      ↓ 原子领取
Node Worker
      ↓ 按任务加载 Skill、上下文和工具白名单
Pi AgentSession
      ↓ 只能调用受限业务工具
OpenCLI / 模型 / Supabase
      ↓
程序核验最终状态 → 人工决定是否进入下一步
```

这张图最重要的信息不是技术栈，而是三条边界：页面一次只发起一个步骤；Agent 只能使用当前任务的工具；程序执行成功不等于人工审核通过。

## 二、沿主线讲：需求分析 → 方案设计 → 开发实现 → 测试验证

## 阶段一：需求分析——先决定不做什么

### 当时面临的问题

最初很容易把项目理解成“小红书自动化工具”：自动抓取、自动改写、自动发布。但继续分析后，我发现最需要解决的不是发布动作，而是发布前的信息组织和内容决策。

### 我的判断

我做了三个范围决策：

1. 不做自动发布、自动点赞、关注、收藏或评论。
2. 不做无人值守、大规模抓取，只做人工触发、范围受限的调研。
3. 不一开始建设万能内容平台，而是底层可扩展、第一条链路只把漫画做深。

### 放弃的方案

- **全自动运营 Agent**：演示效果强，但平台风险、版权风险和错误成本高。
- **完全漫画专用的数据模型**：第一版简单，但第二个账号接入时会重构。
- **一开始做通用工作流编辑器**：扩展性看似更强，但没有真实使用反馈，容易过度设计。

### 结果

项目形成了清晰定位：它是人机协作的内容准备工作台，不是替人做最终决策的自动运营机器人。这一判断也决定了后面的状态机、人工关卡和工具权限设计。

### 这体现了我怎样的 AI Coding 能力

我没有让 AI 自己决定产品范围，而是把自己的业务经验变成约束：什么值得自动化、什么必须由人负责、第一版做到哪里算完成。AI 可以生成方案，但范围判断由我做。

## 阶段二：方案设计——从页面功能升级为业务系统

### 决策点一：为什么使用 React + Supabase

#### 当时面临的问题

我需要一个可实际操作的工作台，同时希望成本低、部署简单，并支持登录、结构化数据、图片存储和用户隔离。

#### 我的选择

- React + TypeScript + Vite 构建交互式工作台；
- Cloudflare Pages 托管静态前端；
- Supabase 提供 Auth、PostgreSQL、私有 Storage 和 RLS；
- AI 密钥和 Service Role 只留在服务端 Worker，不进入浏览器。

#### 放弃的方案

- **纯本地 SQLite + 文件夹**：简单，但不利于多设备使用、在线部署和权限隔离。
- **Next.js 全栈部署**：能力更完整，但当前主要是前端工作台和本地伴随 Worker，Vite + Pages 更轻。
- **把真实数据存在仓库 JSON 中**：部署方便，但不可并发、不可安全保存素材，也没有稳定迁移能力。

#### 结果

前端可以像普通后台一样完成增删改查和审核，Cloudflare 只负责页面，真实业务状态由 Supabase 管理。底层数据模型也能支持两个独立账号。

### 决策点二：为什么业务状态和 Agent 状态必须分开

#### 当时面临的问题

如果把模型调用成功直接等同于业务完成，就会出现“模型生成了 Brief，所以自动审核通过”之类的错误状态推进。

#### 我的选择

我将状态拆成两层：

- Agent 层描述任务有没有排队、运行、成功或失败；
- 业务层描述参考是否保留、采集是否完整、Brief 是否通过、草稿是否审核。

#### 结果

一次采集失败不会推翻“这篇参考值得保留”的人工判断；一次 Brief 生成成功也只会得到 `candidate`，不会自己变成 `approved`。这使系统可以安全地把 AI 放进真实业务流程。

### 决策点三：为什么不用一个万能 Agent

#### 当时面临的问题

完整运营链路很长：调研、采集、选题、Brief、草稿都有不同前置条件和副作用。如果把它们全部交给一个 Agent，它的权限太大，也很难定位失败发生在哪里。

#### 我的选择

我把它拆成六类后台任务，每次只完成一个步骤；每类任务拥有独立 Skill、工具白名单、成功条件和停止条件。

#### 放弃的方案

- **一个 Prompt 生成全部结果**：上下文大、过程不可见，部分失败难处理。
- **一个长期 Agent 接管所有内容对象**：权限边界模糊，错误可能跨步骤扩散。
- **全部写成固定程序**：可靠但无法很好处理语义判断、资料差异和生成任务。

#### 结果

项目采用混合架构：固定、可验证的动作由程序负责；需要理解上下文的选择和生成由模型负责；人负责审核和发布。

## 阶段三：开发实现——我怎样驾驭 AI，而不是被 AI 带着走

### 1. 我给 AI 的不是一句“帮我做个网站”

我逐步把需求写成工程 Spec，每类任务必须回答：

- 谁在什么入口发起；
- 作用于哪个账号和业务对象；
- 需要满足哪些前置条件；
- 能读取哪些可信数据；
- 允许使用哪些工具；
- 会产生哪些副作用；
- 什么数据库状态才算成功；
- 遇到什么情况必须停止并交还给人。

我让 AI 在这些边界内生成和修改代码，再通过代码审查、测试、构建和真实数据检查判断是否接受。AI 是高效率的实现者，不是需求和验收标准的所有者。

### 2. 我在工程中搭建了怎样的 Harness

我没有依赖模型“自己听话”，而是给它搭了一套运行护栏：

- 项目规则规定完整流程和人工关卡；
- Skill 固化各业务步骤的证据、输出和停止条件；
- Worker 按任务注入上下文与工具，不加载全部能力；
- 模型不能自己选择用户和目标对象 ID；
- 工具侧校验用户、账号、对象状态和输入 Schema；
- 任务有租约、心跳、进度、错误和工具调用预算；
- 数据库限制同一对象不能同时存在两个活动任务；
- 最终由程序检查数据库状态，不相信模型仅用文字说“完成”。

我的核心思路是：模型可以不确定，但它行动的环境必须可控、可观察、可验证。

### 3. 长任务不是一个大函数，而是可恢复协议

素材采集要经历浏览器读取、正文保存、逐图分析、上传和写库。最早把它包在一个大工具里时，只要中间失败，Agent 只能知道“失败了”，不知道哪些图片已经保存。

后来我把它拆成：

1. 观察当前采集状态；
2. 准备正文和图片清单；
3. 按位置处理一张图片；
4. 最终检查所有预期位置。

工具会跳过已完成位置，同一会话复用视觉分析，写入响应不确定时先查询数据库。一次真实运行中，系统保留了已有第 1 张图，继续补齐剩余 6 张，并核验 1—7 每个位置恰好一条。

这段经历让我真正理解：Agent 的恢复能力不是多加几次 retry，而是把副作用拆小、让状态可观察、让每一步可核验。

## 阶段四：测试验证——怎么证明 AI 生成的代码值得信任

### 1. 四层验证

我没有用“页面能打开”作为交付标准，而是做四层验证：

1. **静态验证**：TypeScript、lint、生产构建。
2. **自动化测试**：队列、租约、重试、恢复、业务规则和报告逻辑。
3. **数据核验**：读取真实数据库检查素材完整性、来源位置和重复记录。
4. **业务验收**：通过页面和 Worker 执行真实流程，检查人工关卡和最终对象状态。

截至最后一次完整验证，项目有 17 个测试文件、54 项自动化测试通过，构建、Worker 类型检查和 lint 通过。

### 2. 我没有用测试数量冒充业务价值

历史数据库里有 19 次任务，6 次成功、13 次失败。但它们来自不同开发阶段，而且没有可靠版本标签，因此我没有把 31.6% 当成当前成功率，也没有删除失败样本。

当前可以确认的是：

- 7 条完整采集参考的预期图片位置全部齐全；
- 49 条带来源位置的素材没有位置重复；
- 最新执行报告开始记录代码版本、模型、Skill、尝试次数、错误分类、恢复次数和阶段耗时。

下一步需要在最新版本上重新跑六类任务，并用 10—20 个固定样本比较人工流程与工作台，才能回答节省了多少时间、内容质量是否提升。

## 三、两个最值得讲的真实弯路

面试中不要把所有修复都罗列出来，重点讲两个有完整因果链的案例。

## 弯路一：把“没有结果”误认为模型额度问题

### 表面现象

一次素材采集长时间没有结果。因为此前遇到过模型额度不足，很容易直接判断为模型服务问题。

### 我如何调查

我没有继续重复点击，而是检查任务记录、领取次数和事件：任务一直处于 `queued`，领取次数为 0，也没有运行事件。这说明它根本没有进入模型调用。进一步检查发现本机 Worker 没有运行，历史日志也存在数据库网络异常导致 Worker 退出的路径。

Worker 恢复后，任务被成功领取，随后才真正收到模型额度不足错误。这是两个完全不同的故障阶段。

### 我如何修正系统

- Worker 领取异常后改为退避重连，而不是整个进程直接退出；
- 页面区分“排队未领取”和“运行超时”；
- 按时间显示运行事件；
- 失败信息按额度、登录、权限、网络和业务错误分类；
- 页面给出对应操作建议。

### 这个弯路说明了什么

AI 系统不能只展示一个“失败”状态。必须知道失败发生在排队、模型、工具还是业务写入阶段。我的价值不是让 AI 再试一次，而是通过证据推翻了最初假设，并把诊断能力沉淀进产品。

## 弯路二：以为持久化队列就等于可靠执行

### 最初做法

第一版加入 `agent_runs` 后，任务可以被数据库保存和重新领取。我一度以为这已经解决了页面刷新和 Worker 中断问题。

### 后来发现的问题

持久化任务不代表副作用自动幂等，也不代表旧 Worker 失去租约后不会继续写。如果一个 Worker 卡在模型调用中，任务租约过期后被另一个 Worker 领取，旧 Worker 恢复时仍可能写入结果。前端的“先查询再插入”也挡不住并发双击。

### 我如何修正系统

- 增加独立租约心跳；
- 续租、成功和失败写入必须匹配当前 Worker；
- 关键业务写入前再次校验执行权；
- 用数据库部分唯一索引约束同一对象的活动任务；
- 冲突请求复用已有任务；
- 对素材采用稳定位置、固定 ID、写前检查和最终完整性核验。

### 这个弯路说明了什么

可靠性不是“加一张任务表”，而是要理解至少一次执行、租约竞争和重复副作用。AI 可以很快生成队列代码，但如果人不理解这些语义，很容易得到一个看似专业、实际有竞态条件的实现。

## 四、我真正会 AI Coding 的证据

如果面试官问“这不都是 AI 写的吗”，可以从以下六个方面回答。

### 1. 我能把模糊需求变成边界清楚的 Spec

我不是只描述页面，而是定义用户、业务对象、前置条件、可信输入、工具权限、副作用、成功条件和停止条件。这决定 AI 生成什么，也决定我如何验收。

### 2. 我能为长任务管理上下文和拆分粒度

我把项目按“产品层 → 数据层 → 执行层 → 工作流”逐步推进，每次修改控制范围；复杂采集再拆成观察、单步处理和最终核验，避免 AI 一次改动过大或在失败后失去上下文。

### 3. 我不会盲信 AI 给出的架构

我会追问：这个规则在 Prompt 里还是代码里？模型能否伪造对象 ID？两个 Worker 会不会同时写？重试是否会重复副作用？页面刷新后状态在哪里？这些问题推动了工具校验、数据库约束和状态恢复。

### 4. 我会用证据纠正 AI 和自己的错误假设

任务无结果时，我根据领取次数和事件证明它没有调用模型；有队列后，我通过竞态分析发现持久化不等于可靠；恢复测试中，我检查数据库每个图片位置，而不是相信 Agent 回复。

### 5. 我能控制 AI 产出的工程质量

每批修改运行对应测试、构建、类型检查和 lint；Git 按功能批次提交；数据库变更通过迁移管理；历史失败不删除；指标带代码版本，确保后续可以比较。

### 6. 我知道何时不该用 AI

发布、账号验证和最终审核留给人；固定下载、写库与完整性检查交给程序；只有语义理解和内容生成交给模型。会 AI Coding 不等于把所有逻辑交给模型，而是知道模型应处于系统的什么位置。

可以用一句话收束：

> AI 提升了我的实现速度，但项目的范围、架构边界、失败语义、验收标准和最终质量由我负责。我不是在展示 AI 写了多少代码，而是在展示我如何把 AI 组织成一个可控的工程生产力。

## 五、面试追问准备

## 1. 验证与评估

### 你怎么确认 AI 生成的代码是对的？

我不通过“代码看起来合理”判断，而是先把正确性写成不变量。例如同一目标最多一个活动任务、旧 Worker 不能写入、每个预期图片位置恰好一条、Brief 生成后只能是候选状态。然后用测试、类型检查、迁移约束和真实数据库查询验证这些不变量。

### 你怎么证明项目有效？

工程上已经证明链路可运行、数据可以完整追溯，并处理过真实失败；业务价值仍要通过配对实验确认。我计划固定 10—20 个任务，比较人工流程和系统流程的人工操作时间、等待、返工、完成率及 Brief 质量，并保留失败样本，避免幸存者偏差。

### 为什么不用模型自己评价生成质量？

模型可以辅助检查格式或引用，但不能作为自身价值的唯一裁判。最终要由人工按照预先固定的事实正确性、引用支持度、可用性和修改时间标准评审。

## 2. 边界与异常

### 空输入或不满足前置条件怎么办？

页面和工具双重检查。即使绕过前端，Worker 工具仍会核验账号、漫画、参考完整性、Brief 审核和素材状态，不满足就停止，不调用后续模型或写入。

### 重复点击怎么办？

页面执行中禁用按钮只是体验层；真正保证来自稳定目标键和数据库活动任务唯一约束。发生冲突时返回已有任务，而不是再插入一条。

### 模型或网络超时怎么办？

只读请求可以有限重试；写操作和可能仍在执行的浏览器动作不会盲目重放。错误会分类为网络、超时、额度、认证、访问限制或业务校验，并给用户不同建议。

### Worker 中断怎么办？

任务记录仍在数据库，租约过期后可重新领取。支持恢复协议的流程会先观察业务状态并跳过已完成副作用。当前还不是完整的 Pi 会话断点续跑，这是明确的系统边界。

## 3. 真正上线还差什么

### 可靠性

- Worker 进程守护、健康检查和告警；
- 更完整的跨进程恢复与补偿；
- 数据备份、迁移演练和日志保留策略；
- 六类最新版本真实验收和故障注入。

### 性能

- 将每张卡片查询任务改为批量查询；
- 页面路由懒加载，减少前端包体积；
- 素材缩略图、分页和缓存；
- 当单机低并发假设失效时，再评估专用队列或工作流引擎。

### 产品

- 完成人工效率与内容质量对照实验；
- 增加账号级统计与内容效果闭环；
- 有足够样本后再做推荐或自动排序，不用少量数据假装智能。

### 合规与安全

- 保持人工触发和手动发布；
- 不绕过登录、验证码和访问限制；
- 保留素材来源与二次创作边界；
- Service Role 与模型密钥不进入浏览器和日志。

## 六、推荐的现场讲述版本

下面这段适合控制在 4—5 分钟，之后等待面试官选择方向深挖。

> 我做的是一个个人创作者 AI 内容运营工作台。这个项目来自我真实的实习和账号运营经历：以前做一篇漫画内容，要在浏览器里调研别人发过什么，把图片存在本地，靠记忆区分漫画和章节，再临时整理选题和文案。真正的问题不是模型不会写文案，而是资料散落、过程不可追踪，失败后容易重复操作，最后也无法说明一个 Brief 基于哪些参考和素材。
>
> 所以我先做了范围判断：不做自动发布和批量互动，不追求全自动运营；底层按多账号设计，但第一条链只把漫画做深。最终产品是一个 React 工作台，Supabase 管理认证、业务数据和私有图片，本地 OpenCLI 负责人工触发的浏览器调研与草稿暂存。整个流程覆盖漫画档案、参考调研、笔记与图片采集、选题、Brief、草稿和人工审核；最后在创作者中心修改并手动发布。
>
> 第一版其实只是页面收集输入、程序拼 Prompt、调用一次 LLM。输入输出明确时这没有问题。但素材采集和内容生产逐渐变成长任务：它们有前置条件，会产生多个副作用，也可能只完成一部分。继续把逻辑堆在按钮里之后，页面刷新、网络错误和 Worker 中断都很难处理。因此我把它升级成 Worker + Pi Agent：页面只入队一个有边界的任务，Worker 原子领取，按任务注入 Skill 和工具白名单，Agent 只能调用受限工具，最终由程序核验数据库状态。Agent 的执行成功和人工审核通过是两套状态。
>
> 这里最难的不是接模型，而是搭 Harness。我通过对象绑定、工具权限、租约心跳、活动任务唯一约束、写前执行权校验、错误分类、工具预算和最终核验，把模型的不确定性包起来。比如素材采集最初是一个大工具，中途失败后不知道哪些图片成功了。后来我将它拆成观察状态、准备清单、逐张处理和最终核验。一次真实恢复运行中，系统保留已有第 1 张，补齐剩余 6 张，并确认 1 到 7 每个位置恰好一条。
>
> 另一个真实弯路是，一次任务长时间没结果，最初很容易以为又是模型额度问题。但我检查任务发现它一直 queued、领取次数为 0，实际是 Worker 没运行；Worker 恢复后才真正收到额度错误。这个问题让我把排队、运行和业务失败彻底分开，并补了重连、进度事件和可操作的错误提示。后来我又发现持久化队列不等于可靠执行，于是增加租约心跳和数据库级并发去重，防止旧 Worker 或重复点击产生重复写入。
>
> 验证方面，我给关键不变量写测试，而不是只看页面。截至最后一次完整验证，有 17 个测试文件、54 项测试，构建、Worker 类型检查和 lint 都通过。历史数据库中 7 条完整采集参考的图片位置全部齐全，49 条带来源位置的素材没有位置重复。但 19 条历史任务跨越不同开发版本，所以我没有拿它们宣称当前成功率，而是补了版本化执行报告。下一步要在最新版本上跑六类真实验收，并用固定样本比较人工耗时和 Brief 质量。
>
> 这个项目让我最大的收获是，AI Coding 不是让模型替我写完代码，而是我负责需求取舍、Spec、架构边界、失败语义和验收，AI 负责加速实现。真正体现能力的，是我能发现 AI 生成方案里的竞态、权限和恢复问题，并把这些判断沉淀成代码、数据库约束和稳定工作流。
