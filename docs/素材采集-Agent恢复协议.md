# 素材采集的 Agent 恢复协议

2026-09-11。本轮仅为 `note_capture` 引入恢复协议，其他工作流不自动获得重试权限。

## 执行过程

Pi 使用四个工具：

1. `inspect_capture_state`：读取当前笔记、预期图片位置、数据库已保存位置、剩余位置和最近错误。
2. `prepare_note_capture`：一次性获取笔记和图片清单，当前会话内缓存；不自动重试导航或采集超时。
3. `process_capture_image(position)`：逐张处理，先查是否入库，再分析上传。Pi 根据返回结果决定检查或重试。
4. `finalize_note_capture`：检查每个预期位置恰好有一条素材，缺图则返回剩余位置；全部齐全后保存正文与结果。

工具结果采用 `ok`、`stage`、`message`、`retryable`、`action`、`preserveCompleted` 等字段。一次可恢复失败不结束 Pi 会话，模型可以调用观察工具并调整下一步。每步最多三次尝试，总工具调用最多 120 次；工具按顺序执行，避免模型并发调用同一位置。

## 数据与错误处理

- 已入库图片在调用视觉模型前跳过；本会话已得到的视觉分析也缓存复用。
- 同一图片在当前会话内使用固定素材 ID 和存储路径。数据库写入响应不确定时，先查已有结果；不立即删除可能被成功记录引用的图片。
- 普通进度写入失败返回警告，保留业务结果；任务执行权检查仍是硬条件。每次工具操作前更新并检查绑定 Worker 的租约。
- 结构化错误读取 message、code、details 等字段，避免 `[object Object]`；输出中隐藏 URL。
- 仅对该恢复流程，在最终数据库核验成功后忽略已经恢复的历史错误。模型自行说“完成”不构成成功。
- 额度、权限、登录、验证或访问拒绝需要停止；导航超时也不盲目重放，因为原请求可能仍在执行。

## 边界

既有素材跨任务保留，图片清单、视觉分析和固定写入 ID 仅保留在当前会话。此版本不提供完整的跨进程断点恢复、独立租约心跳或全局 exactly-once 保证。长任务页面等待可能先超时，任务本身仍由 Worker 执行。

修改涉及 `AGENTS.md`、`agent/RUNTIME.md`、两个采集 Skill、`agent/additionalWorkflows.ts` 和新增 `agent/captureRecovery.ts`。旧中文全文汇总是 9 月 9 日快照，当前规则请以源文件和本说明为准。

## 验证

34 项测试、Worker 类型检查、前端构建和 lint 通过；两个修改的 Skill 格式有效。模拟故障测试实际经过拆分后的工具代码，验证第一张已提交但响应报错后，检查状态能跳过该图片，并继续第二张，最终完成；这不替代真实模型自主恢复的验收。

### 真实采集结果（2026-09-11）

重启更新后的 Worker 后，对之前仅保存一张图的笔记《隔一段时间就拿出来看看的漫画！我超爱！》执行真实 Pi 采集。运行 `41113e03-6461-4df5-84fd-e7d077b7a58f` 已成功结束，输出 `verified: true`。数据库核验得到位置 1—7 各一条素材，没有重复；原第一张素材 ID 保持不变，新增剩余六张。参考笔记状态为 `detailed`，图片数为 7，错误为空。

本次真实运行验证了 Pi 多步工具调度、复用已有素材以及最终完整性核验；没有据此宣称所有瞬时故障均已真实触发并恢复。数据库响应不确定等恢复分支目前由故障注入测试覆盖。
