# Creator Ops Studio：面试讲述与深挖手册

> 文档定位：帮助我把这个 AI Coding 项目讲成一段可信的工程实践，而不是“让 AI 帮我做了一个 Demo”。
>
> 证据口径：内容依据历史会话、当前代码、Git 提交、数据库基线和项目内验证文档整理。凡是尚未经过最新版本真实验收或对照实验的数据，均明确标注，不夸大。

## 一句话定义

Creator Ops Studio 是一个面向个人创作者的、人机协作式内容运营工作台。它把漫画内容运营中分散的漫画发现、参考调研、笔记与图片采集、选题、Brief、草稿和人工审核，组织成一条可追踪、可恢复、有证据链的工作流；第一条完整业务链服务漫画账号，底层模型可以继续复用到“求职 + 学习 + 技术”账号。

它不是自动发帖工具，也不是套壳文案生成器。系统支持由人主动把已保存文案和最终选图暂存到创作者中心草稿箱；Brief 审核、选图、最终修改与公开发布仍由人决定。

## 1. 面试开场：这是干什么的、我做了什么、结果是什么

### 30 秒版本

我基于自己做小红书内容运营的真实经历，做了一个个人创作者内容运营工作台。它把原来依赖收藏夹、表格和人工记忆的漫画调研、素材整理、选题、Brief 和文案生产串成一条工作流。我不仅做了 React + Supabase 的业务页面，还把最初的单次 LLM 调用升级成了 Worker + Pi Agent 的后台执行架构，用任务队列、Skill、受限工具、人工审核、租约、幂等、失败恢复和执行报告约束 Agent。当前代码有 17 个测试文件、54 项自动化测试通过；历史真实数据中，7 条完整采集笔记的图片位置全部齐全，49 条带来源位置的素材没有位置重复。六类原有任务和新增的 Pi 草稿暂存仍需按最新版本验收，所以我不会把工程测试说成生产成功率。

### 1 分钟版本

这个项目来自一个非常具体的问题：我实习时做过小红书选题、素材、文案和发布的全流程，自己也在运营漫画账号。我发现真正耗时的不是调用一次模型生成文案，而是如何持续找到值得做的题、保存证据和素材、知道每一步做到哪里、失败后不重复写入，以及保证最终仍由人审核。

所以我做了 Creator Ops Studio。前端是 React + TypeScript + Vite，Supabase 负责认证、PostgreSQL、私有图片存储和用户隔离；本机 OpenCLI 复用已登录浏览器做低频、人工触发的平台调研和草稿暂存；Node Worker 从数据库领取任务，每个任务创建一次 Pi AgentSession，只注入对应 Skill 和工具白名单。草稿暂存也走任务队列，由 Pi 按独立 Skill 和受限工具执行。Agent 的执行状态和选题、Brief 等业务状态分开存储，模型生成成功不等于人工审核通过。

我的核心工作不是只写页面，而是把一个模糊的内容运营需求拆成状态机、数据模型、九个项目 Skill、七类后台任务和明确的人审关卡，并补上租约心跳、并发去重、错误分类、有限重试、页面刷新恢复、逐图采集恢复和版本化执行指标。项目已经证明这条链路能够处理真实数据，也试过将一份草稿暂存到创作者中心；但新的 Pi 暂存链路仍需完整验收，日常提效也需要对照实验，不能直接报节省多少时间。

### 3 分钟版本：为什么做 → 架构 → 我的工作 → 难点 → 结果 → 优化

**为什么做。** 我不是先想“做个 Agent 项目”，而是先有真实运营问题。漫画内容生产的信息散落在搜索结果、收藏、图片文件和临时文案中；同一篇参考是否采集完整、图片是否重复、一个 Brief 基于哪些证据，往往无法追溯。与此同时，自动发布和无人值守抓取风险高，也不是个人运营最需要解决的问题。因此我把目标定为“内容准备工作台”，重点优化发布前的决策和资料组织，保留人工审核和手动发布。

**架构。** 页面只负责发起一个有边界的步骤和展示状态；任务进入 Supabase 的 `agent_runs`，Node Worker 原子领取后，根据 `run_type` 加载对应 Skill、工具白名单和成功条件，再创建单次 Pi 会话。工具层负责用户和对象绑定、业务校验、数据库写入、OpenCLI 浏览器访问和图片处理；Agent 不能自由拿对象 ID，也不能越过人工关卡。`agent_run_events` 保存用户可理解的进度，页面轮询并在刷新后重新挂接任务。业务数据仍进入漫画、参考、素材、选题、草稿等领域表，而不是把聊天记录当数据库。

**我的工作。** 我用 AI Coding 完成实现，但需求定义、边界设计、验收标准和取舍由我负责。我先把实习流程抽象成通用内核与漫画垂直链路，再设计数据库和 RLS、页面状态流、Skill、Worker 和 Agent 工具；随后根据真实失败逐轮补可靠性，包括 Worker 断连、任务重复提交、租约竞争、旧 Worker 越权写入、额度与登录错误、页面刷新丢状态、素材部分写入等问题；最后增加执行报告、版本标签和只读基线脚本，让后续优化能够被比较而不是靠感觉判断。

**核心难点。** 第一是把自然语言需求变成可执行规范，而不是一个大 Prompt；第二是处理长任务和部分成功，例如七张图已经存了一张时，下一次不能全部重做；第三是给 Agent 建 Harness，让它只在受控环境中行动；第四是区分“程序执行成功”和“业务上被人接受”；第五是建立“不自证”的评估口径，自动化测试只能证明代码性质，不能代替内容质量和人工效率实验。

**结果。** 当前七类页面任务已经接入统一执行层，覆盖档案补全、参考调研、笔记素材采集、选题、Brief、草稿生成和草稿暂存；具备队列、进度、租约、活动任务去重、页面刷新恢复、失败建议和版本化指标。自动化验证为 17 个测试文件、54 项测试，加上构建、Worker 类型检查和 lint。历史数据库快照中有 19 次任务，6 次成功、13 次失败；这批样本跨越开发阶段，不能作为当前版本成功率。可确认的数据完整性是：7 条完整采集参考的预期图片位置均齐全，49 条带来源位置的素材没有位置重复。项目还真实完成过一次“保留已有第 1 张、补齐剩余 6 张、最终核验 1—7 各一条”的恢复运行。

**还能优化。** 短期要在最新版本上把六类流程逐一真实验收，并做断网、Worker 重启、重复点击等故障注入；中期用 10—20 个固定样本比较人工流程与工作台的人工耗时、完成率、返工和 Brief 质量；工程上可以把每张卡片的任务查询改为批量查询、做路由懒加载、增加进程守护和跨进程断点恢复。如果任务规模和并发明显增长，再考虑从 PostgreSQL 队列迁移到专用队列或工作流引擎，而不是现在过早引入复杂基础设施。

## 2. 为什么这个项目不是 Demo

面试官可能会问：“这是不是一个 UI 加几个 Prompt？”我的回答是：判断它是不是 Demo，不看页面数量，而看它是否处理了真实状态、真实失败和持续运行。

| 判断维度 | Demo 常见做法 | 本项目的工程落地 |
|---|---|---|
| 数据 | 临时 JSON 或聊天上下文 | PostgreSQL 领域表、私有 Storage、来源与版本快照 |
| 身份与隔离 | 单机假数据 | Supabase Auth、RLS、用户/账号/业务对象绑定 |
| AI 调用 | 一个 Prompt 直接返回 | 按任务加载 Skill、限定工具、代码校验输入输出 |
| 长任务 | 页面等待一个请求 | 持久化任务队列、Worker、租约、进度事件 |
| 失败 | 弹出“出错了” | 错误分类、有限重试、恢复建议、部分成功保留 |
| 并发与重复 | 依赖按钮禁用 | 数据库活动任务唯一约束与幂等目标键 |
| 页面刷新 | 状态丢失 | 按业务对象恢复活动任务并继续轮询 |
| 业务审核 | 模型输出即完成 | Agent 状态与业务状态分离，Brief 保持 `candidate` |
| 可观测性 | 看控制台日志 | 运行事件、执行报告、版本/模型/Skill/耗时指标 |
| 评估 | 展示一次成功 | 保留失败样本，建立基线与人工对照实验方案 |

最能证明它不是 Demo 的不是“用了 Agent”，而是系统能够回答这些问题：谁发起了任务？它作用于哪个业务对象？现在做到哪一步？已经产生了哪些副作用？失败是否可重试？重复执行会不会产生重复数据？模型说完成后，数据库是否真的完整？谁来决定结果可不可以发布？

## 3. 从需求到 Spec：我是怎么做的

### 3.1 先写用户工作流，不先写技术方案

最初需求来自真实行为：

> 选择漫画 → 调研别人发过什么 → 找对应素材 → 形成选题与文案 → 手动发布 → 记录效果。

我先做了两个产品取舍：

1. 底层做成可扩展的多账号内容模型，但第一条完整链只做漫画账号，避免一开始做“万能平台”。
2. 不做自动发布、批量互动和无人值守抓取，把高风险动作留给人。

### 3.2 把流程拆成领域对象和状态

我没有把所有内容塞进一张表，而是识别出账号、漫画、参考、素材、选题、Brief、草稿、发布和指标等对象。然后为不同对象定义独立状态：

- Agent 任务：`queued / running / succeeded / failed / cancelled`
- 参考审核：`candidate / kept / rejected`
- 参考采集：`list_only / detailed / failed`
- Brief：`candidate / approved / rejected`
- 草稿审核：`draft / review / approved / rejected`

这样“一次 Agent 成功”不会自动变成“内容审核通过”，采集失败也不会推翻“这条参考值得保留”的人工判断。

### 3.3 每个任务 Spec 至少写清八件事

我为每种工作流都要求明确：

1. **入口与授权**：谁在什么页面、对哪个对象发起。
2. **前置条件**：例如生成草稿前 Brief 必须已审核、素材必须可用。
3. **可信输入**：哪些字段来自数据库，哪些网页内容只能作为不可信数据。
4. **工具白名单**：该任务能观察和修改什么。
5. **输出 Schema**：必填字段、长度、枚举和来源引用。
6. **副作用**：会写哪些表、上传哪些文件。
7. **成功条件**：不能只相信模型文本，必须由程序核验最终状态。
8. **停止条件**：额度、权限、验证码、访问拒绝和人工关卡必须停止。

Skill 文档承载语义规则，TypeScript 工具和数据库约束承载强约束。Prompt 不是权限系统，关键规则不能只写在 Prompt 里。

### 3.4 用验收标准反推实现

例如“采集一篇参考笔记”并不以 Agent 回复“完成”为结束，而以这些条件为准：正文已保存；预期每个图片位置恰好有一条素材；来源笔记和图片位置可追溯；重复执行不会再次处理已完成位置；最终数据库核验通过。这个成功定义直接推动了逐图工具、固定素材 ID、位置唯一性和 `finalize` 核验的设计。

## 4. 长任务怎么拆

### 4.1 纵向拆成有限业务步骤

整个链路没有交给一个“万能 Agent”一次跑完，而是拆成六类后台任务：

1. 漫画官方档案补全
2. 小红书参考调研
3. 笔记与图片采集
4. 选题生成
5. Brief 生成
6. 草稿生成

每次页面操作只授权一步，下一步由用户确认。这既控制成本和风险，也让失败范围更小。

### 4.2 横向拆成观察—行动—核验

素材采集是最典型的长任务。我把原来的“大工具一次包办”拆成：

- `inspect_capture_state`：看已经完成了什么、还缺什么、最近为何失败。
- `prepare_note_capture`：获取正文与图片清单，并在当前会话缓存。
- `process_capture_image(position)`：逐张分析、上传和写库；已完成位置直接跳过。
- `finalize_note_capture`：核验每个预期位置恰好一条，完整后才更新最终状态。

单步最多三次尝试，总工具调用数有预算；额度、登录、权限、验证码和访问拒绝不盲目重试。数据库响应不确定时先查状态，而不是马上再写一次。这比简单的 `try/catch + retry` 更接近可恢复工作流。

### 4.3 区分会话恢复、任务恢复和业务恢复

- 页面恢复：刷新后重新查询活动任务并继续显示。
- 任务恢复：租约过期后可被 Worker 重新领取。
- 业务恢复：重新执行前先观察数据库，跳过已经完成的副作用。
- 会话恢复：当前 Pi 会话使用内存存储，尚不支持从某条历史工具消息继续。

我会主动说明这个边界：现在实现的是基于持久化业务状态的恢复，不是完整的 Agent 会话断点续跑，也没有全局 exactly-once 保证。

## 5. Harness 是怎么在工程中落地的

这里的 Harness 不是一个单独的框架名，而是“围绕不确定模型建立的可控执行环境”。它由以下几层共同组成：

### 上下文 Harness

- 项目级 `AGENTS.md` 规定总流程、安全边界和人审关卡。
- 每个 Skill 只描述一种业务能力的输入、证据、输出和停止条件。
- Worker 不自动加载全部全局能力，而是按任务注入运行规则、当前 Skill 和少量工具。
- 网页正文、元数据和工具输出一律视为不可信数据，不能反向成为系统指令。

### 工具 Harness

- 每类任务有工具白名单，模型不能任意访问系统。
- 用户、账号和业务对象 ID 由 Worker 绑定，不能相信模型自己传入的 ID。
- Service Role 和模型密钥只在 Worker，不能通过 `VITE_*`、日志或提示词进入浏览器。
- 生成前后由代码校验状态、必填字段、长度、枚举和证据引用。

### 执行 Harness

- `agent_runs` 是持久化队列和运行台账，`agent_run_events` 是进度记录。
- `FOR UPDATE SKIP LOCKED` 原子领取任务；租约、心跳和 Worker 所有权保护防止旧执行者覆盖新结果。
- 数据库部分唯一索引防止相同对象出现多个活动任务。
- 只读外部请求允许有限重试，写操作不自动盲目重放。
- 模型“自称完成”不算成功，最终必须检查数据库结果。

### 产品 Harness

- 页面只允许发起有边界的一步。
- 刷新后恢复运行状态，执行中禁用冲突操作。
- 失败提示不仅显示错误，还告诉用户是等待额度、重新登录、检查权限还是重新执行。
- Agent 执行成功与人工审核通过分开，系统不能自行发布、点赞、关注或评论。

### 评测 Harness

- 单元与集成测试覆盖租约、重试、恢复、报告和业务规则。
- 执行报告记录代码版本、模型、Skill、尝试次数、错误分类、恢复次数和阶段耗时。
- 只读基线脚本按版本和任务类型汇总，旧样本无版本标签时明确隔离。
- 保留失败样本，不为了展示删除历史失败。

一句话总结：我没有试图让模型变得确定，而是让模型的不确定性被状态机、工具权限、校验、预算、日志和人工关卡包起来。

## 6. 做完以后，怎么变成稳定 Workflow

我把“能跑一次”变成“可重复运行”的过程分为五层：

1. **流程固化**：真实操作流程写成 Skill 和前置条件，而不是散落在页面按钮与 Prompt 中。
2. **状态固化**：业务数据和执行数据持久化，页面、Worker 或会话退出都不等于状态丢失。
3. **失败固化**：错误分类为网络、超时、额度、认证、访问限制和业务校验；只对安全、可恢复的步骤有限重试。
4. **运维固化**：统一启动方式、环境变量、Worker 日志、迁移、构建和测试命令；每批修改提交 Git，便于回滚。
5. **评估固化**：新任务带发布版本、模型和 Skill 信息，基线脚本可复跑；未来用固定样本做人工对照与故障注入。

当前仍未完全解决的稳定性问题包括：Worker 不是系统服务，电脑重启后需重新启动；没有完整跨进程会话恢复；本地浏览器桥仍受登录状态和页面变化影响；最新版本尚未完成六类流程的系统化真实验收。面试时主动讲这些限制，反而能体现工程判断。

## 7. 核心难点与关键决策

### 难点一：通用性与落地深度如何平衡

我的选择是“通用内核 + 漫画垂直首发”。账号、选题、参考、素材、草稿和指标是通用实体；漫画、章节、人物、更新时间等是垂直属性。这样既能复用到第二个账号，又不会为了未来可能性先做复杂的动态工作流编辑器。

### 难点二：为什么不是所有步骤都交给 Agent

固定、可验证的动作更适合程序；需要结合上下文做语义判断的动作才交给模型。例如下载、逐图写库和最终完整性检查由工具代码执行，模型负责根据状态选择下一步和生成结构化内容。这种混合架构比“Agent 自由规划一切”更可控。

### 难点三：高权限 Worker 如何保证数据隔离

浏览器端依赖 RLS，但 Worker 使用 Service Role，不能继续依赖前端权限。因此任务在入队时绑定 `user_id / account_id / target_id`，工具查询和写入时再次校验归属；模型不能选择任意对象。凭证也只存在于 Worker 环境。

### 难点四：如何处理至少一次执行带来的重复副作用

数据库队列和租约本质上更接近至少一次执行。我的处理方式不是声称实现了 exactly-once，而是通过活动任务唯一约束、稳定幂等键、写前状态检查、固定素材 ID、已完成位置跳过、执行权校验和最终完整性核验，把重复副作用控制在业务可接受范围。

### 难点五：如何证明优化有效

不能拿自动化测试数量证明业务价值，也不能用跨版本历史任务直接比较。因此我先补版本化运行指标，并把 19 条无版本标签的旧任务单独归类；下一阶段再用固定输入比较人工流程与工作台、固定流程与 Agent，分别测人工时间、完成率、恢复率、重复副作用和内容质量。

## 9. 高频深挖问答

### Q1：为什么从直接 LLM 调用升级成 Agent？

简单的 Brief 生成仍然适合一次 LLM 调用。升级不是为了追热点，而是因为任务开始包含观察、工具调用、部分成功和恢复。例如素材采集需要先看已有图片，再逐张处理，失败后决定检查还是重试。Worker 和数据库提供队列、租约与记录，Pi 提供会话和工具调用循环。两者组合解决的是“有状态任务”，不是让所有生成都变成 Agent。

### Q2：为什么用 PostgreSQL 做队列，不用 Redis、Kafka 或 Temporal？

当前是本地、低并发、单用户为主的个人工作台，业务数据已经在 Supabase。使用 PostgreSQL 表和领取 RPC 可以用较小成本获得持久化、原子领取和页面可查询性。代价是重试、租约和监控需要自己实现。若未来出现多机器、高并发、长时间补偿和复杂 DAG，我会再迁移到专用队列或工作流引擎。

### Q3：Skill 和普通 Prompt 有什么区别？

Skill 在这里是可版本化的业务规约，描述适用条件、证据要求、工具边界、输出和停止条件；Prompt 只是一次调用里的文本。更关键的是，Skill 仍不是安全边界，真正的权限、对象绑定、状态检查和写入约束都在工具代码和数据库里。

### Q4：如何防止 Prompt Injection？

外部网页、笔记正文、元数据和工具结果都标记为不可信数据；Worker 只加载当前任务规则和工具白名单；模型不能提供用户或目标对象 ID；工具侧再次校验数据归属与业务状态；外部内容不能修改系统指令或越过人工关卡。

### Q5：页面刷新、Worker 重启会怎样？

页面刷新后会按业务对象查找最近活动任务并重新轮询。Worker 意外退出时，租约过期后任务可以被重新领取，但不是从 Pi 的某条消息继续，而是从持久化业务状态重新观察并执行。只有实现了恢复工具的流程才能安全跳过已完成副作用。

### Q6：如何防止两个 Worker 同时写？

领取时使用行锁和 `SKIP LOCKED`；运行中维护租约和心跳；续租、进度、成功和失败写入都要求匹配当前 Worker；关键业务写入前再验证执行权。即使旧 Worker 在模型调用后才恢复，也不能越权覆盖新 Worker 的结果。

### Q7：怎么处理模型输出不稳定？

先减少模型自由度：只提供必要上下文和少量工具。然后用结构化 Schema、枚举、长度与必填校验约束输出；把来源 URL 等权威值保留在宿主，不让模型重写；最后以数据库状态核验成功。错误重试也只限于可安全重复的只读步骤。

### Q8：AI Coding 中“你”到底做了什么？

AI 帮助我加速代码生成、重构、测试和文档整理，但我负责把真实运营经验转成需求、决定不做什么、划分领域对象和状态、选择架构、定义 Skill 与成功条件、判断哪些规则必须落到代码和数据库、根据真实故障确定优先级，并对产物做测试、Git 管理和事实核验。我的价值不是逐字符输入代码，而是把不确定的 AI 产出组织成可维护、可验证的工程系统。

### Q9：最大的失败是什么？

早期一个采集任务长时间排队，最初很容易误以为是模型额度问题。调查发现任务领取次数为 0，真正现象是 Worker 没有运行；之后 Worker 恢复领取，模型服务才返回额度错误。这个案例让我意识到必须区分排队、运行和业务失败，也推动了重连、事件进度、错误分类和页面提示的实现。另一个教训是，任务持久化不等于副作用幂等，必须显式做租约、状态检查和最终核验。

### Q10：如果再做一遍，会先改什么？

我会更早定义评测基线和版本元数据，在第一次真实运行前就记录代码版本、模型、Skill 和任务规模；同时更早把长任务拆成观察—单步行动—最终核验，而不是先做一个大工具。这样可以减少后期为恢复能力重构的成本。

## 10. 收获了什么

1. **从功能思维转向系统思维。** “能生成一段文案”只是能力，“谁在何时对哪个对象执行、失败怎么办、结果能否追溯”才是系统。
2. **Spec 的核心是边界与验收。** 好的 Spec 不只是写需求列表，而是定义前置条件、可信输入、副作用、成功与停止条件。
3. **Agent 适合处理不确定决策，不适合替代所有程序。** 固定步骤应该代码化，语义判断交给模型，两者通过工具协议衔接。
4. **可靠性来自副作用管理。** 租约、幂等、状态观察、有限重试和最终核验，比继续优化 Prompt 更能决定系统是否可用。
5. **人工审核是产品设计，不是自动化不彻底。** 对内容质量、版权、平台行为和发布结果，人应该保留最终决策权。
6. **评测必须防止自证。** 测试通过不等于业务有效；历史成功不等于当前版本稳定；模型也不能评价自己是否节省了人工。
7. **AI Coding 的上限取决于人的判断。** AI 能快速产出代码，但需求取舍、架构边界、事实核验和质量责任仍需要人承担。

## 11. 后续优化路线

### P0：完成最新版本真实验收

- 六类任务各至少成功运行一次。
- 验证刷新、重复点击、Worker 退出重启、网络异常、额度不足和登录失效。
- 检查页面、运行报告、业务表和 Storage 结果是否一致。

### P1：建立业务价值证据

- 用 10—20 个固定任务做人工流程与工作台配对实验。
- 记录人工操作时间、等待、返工、完成率、重复副作用和最终质量。
- 对 Brief 做事实正确性、证据支持度和人工修改时间评审。

### P2：补生产级运行能力

- Worker 进程守护和健康检查。
- 批量查询卡片任务，减少页面 N 次查询。
- 更完整的跨进程任务恢复与补偿机制。
- 告警、指标看板、数据保留和备份策略。

### P3：规模增长后再演进

- 当单机、低并发假设不成立时，评估专用队列或工作流引擎。
- 将本地 OpenCLI 桥拆为独立伴随服务。
- 在有足够真实样本后，再做自动排序、个性化推荐和发布表现闭环。
